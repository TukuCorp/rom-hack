REA as a Ghidra wrapper, tested on LEAP

2026-10-10 · Windows 11 x64 · Ghidra 12.1.4 PUBLIC · REA 6.3.0 · provider ghidra · targets: testleap.exe (2.38 MB) and leap.exe (168.5 MB)

Confirmed: REA is a wrapper around the Ghidra install, and it works on LEAP. It shells out to our own support\analyzeHeadless.bat, imports an immutable copy of the target into an ephemeral read-only project, and injects its own Java post-script (ReaGhidraBridge.java) that serves the results back over an authenticated loopback socket.

The strongest single check: REA's decompiler output for entry @ 0x61a848 is byte-identical to Ghidra's own — 26,938 characters, 540 lines, same SHA-256 F47A361E…D1E647. REA adds an evidence layer on top; it does not add analysis.

5. What the wrapper adds over raw Ghidra

  • Provenance envelope. Every result carries the subject's SHA-256, the provider identity, an analysis-profile digest, a confidence word (observed / derived) and a limitations list.
  • Typed contracts. analyze_function returns basic blocks, callers/callees, referenced names and strings, and a bounded p-code def-use graph — layers GhidraMCP exposes only as separate endpoints.
  • Composition. trace chains search → references → containing procedure in one call and names its own gap when an address sits outside any function.
  • Stated omissions. Synthetic entry-point references are dropped deliberately, and the reason is written in the result rather than left as a silent gap.

Reading this correctly. REA engaged Ghidra on leap.exe exactly as designed; the limit is the target against the host, not the wrapper. Because REA serves nothing until auto-analysis completes and deletes its project on close, a 169 MB binary means hours per session here. I stopped the run rather than let a 4 GB-heap JVM starve the machine you are working on.

7. Caveats

  • Every CLI invocation is a fresh process, so each of the six operations above paid full import + analysis again — 4.5 to 9 minutes each. An MCP session holding open_binary would pay that once.
  • The --snapshot cache was written (4.5 KB, with binding, entries, workflow_entries) but replaying the identical query still cost 367.9 s against 496.2 s cold — it did not skip provider startup in this configuration.
  • Absolute wall times are inflated by this machine's memory pressure and by a second resident Ghidra server. The identity checks (hashes, addresses, counts) are the load-bearing evidence, not the seconds.
  • Only the Ghidra provider could be tested: Hopper needs macOS and IDA was not configured.
