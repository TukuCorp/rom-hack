REA vs Ghidra on LEAP

Measured 2026-10-10 on this workstation (Windows 11 x64, 8 GB RAM, JDK 21.0.10). Ghidra 12.1.4 PUBLIC · GhidraMCP 7.0.0 · REA 6.3.0 (morluto/rea) with its ghidra provider.

On Windows, REA is a wrapper over Ghidra, not a competing engine. It shells out to analyzeHeadless from the same install, so it inherits Ghidra's analysis and produces the same substantive results — the procedure count and the string-search hits came back identical.

The differences are real but sit in the session layer. REA adds a provenance envelope, typed contracts and explicit limitations. Ghidra, driven through a persistent GhidraMCP session, answers repeat queries about 1000× faster and can serve partial results while analysis is still running. REA refuses to serve anything until auto-analysis completes, and its 330 s default startup deadline is too short for even a 2.4 MB LEAP binary on this host.

For reverse-engineering LEAP here: drive Ghidra directly. Use REA when you want its evidence contracts or its agent workflow, and raise its deadline first.

What this means for REA on leap.exe. REA cannot serve a single query until auto-analysis finishes, and its default deadline is 330 s — against a target where raw Ghidra had not finished after 120 minutes. Making REA usable here means raising REA_GHIDRA_STARTUP_TIMEOUT_MS into the hours, and it pays that analysis cost again for each new session because the project is ephemeral. Ghidra pays it once and keeps the project.

Method

# REA setup (it drives our existing Ghidra 12.1.4 install)
$env:GHIDRA_INSTALL_DIR = "C:\Users\tukum\Downloads\rom-hack\ghidra_12.1.4_PUBLIC"
$env:JAVA_HOME          = "C:\Program Files\Eclipse Adoptium\jdk-21.0.10.7-hotspot"
$env:REA_ANALYSIS_PROVIDER = "ghidra"
npm install --global rea-agents          # 6.3.0, bundles the Windows native addon
rea doctor --json                        # 0 failing ghidra checks; version 12.1.4 detected

# Ghidra baseline, raw
analyzeHeadless.bat ghidra-bench BenchSmall -import "C:\Program Files\LEAP\testleap.exe"

# REA, same target (default deadline first, then raised)
rea inspect "C:\Program Files\LEAP\testleap.exe" --provider ghidra --json
$env:REA_GHIDRA_STARTUP_TIMEOUT_MS = "1500000"
rea search  "C:\Program Files\LEAP\testleap.exe" "ShortInt" --provider ghidra --json

Limits of this comparison

  • One host, one small target, one run each. The absolute seconds are inflated by this machine's memory pressure; the ratios are the portable part.
  • REA was measured through its CLI, where every invocation is a fresh process. An MCP session with open_binary holds the analysis open, which removes the per-query re-analysis cost — I measured the CLI path, so treat 271 s as the worst case, not the intended one.
  • The 386-string gap is a counting difference between the two interfaces, not proof that either engine sees more. Both read the same Ghidra program.
  • Hopper and IDA providers were unavailable on Windows, so REA was only ever tested against the engine Ghidra also uses.
