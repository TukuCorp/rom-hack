# Porting LEAP to Rust

`leap-rs` is a headless Rust port of the computational core of LEAP. It exists so
the same arithmetic can run under agentic control, with Rust memory safety instead
of a Delphi runtime, and with no user interface.

## Read this before believing a green test run

`leap.exe` is a 168.5 MB Delphi (Object Pascal) binary. The decompilation in
`../leap-decompiled/` covers **168,840 of 168,848** functions. Porting all of it
1:1 is a multi-year body of work, not a session.

What this crate actually is: the pipeline (oracle capture, port, parity test), the two
calendar functions, the `.leap` container validation chain behind `TestLEAP`, and a reader
for the model arithmetic the area tables store, together with the registry that says what each
function code in it is and the record reader that puts a number at a named field. That is four
units of work against 168,840 functions. A passing `cargo test` means those pieces agree with
the original over what they have been measured on; it does not mean LEAP has been ported.

## Rules the port follows

1. Every ported function carries its original address and name in the doc comment,
   so any claim can be checked against `../leap-decompiled/index.tsv`.
2. Semantics are reproduced exactly, not normalised. That includes integer widths
   and truncation, strength-reduced arithmetic (the original computes `year mod 4`
   as `AND EAX,0x3`), whether a failure leaves an out-parameter untouched, and the
   1-byte `Boolean` return in `AL`.
3. Every ported function has a parity test asserting bit-for-bit equality of output
   against vectors captured from the original binary. Floating point is compared as
   raw IEEE-754 bits (`f64::to_bits`), never with a tolerance.
4. No function enters the port without oracle vectors, and the test is written and
   seen to fail before the implementation is written.

## Where the ground truth comes from

`src/oracle_calendar.rs` is generated by `tools/capture_oracle.py`; do not edit it by
hand. The tool drives Ghidra `/emulate_function` on the original image, so every
vector is output of the original itself rather than a re-derivation of it.

Current corpus: **310** `IS_LEAP_YEAR_VECTORS`, **487** `DAY_NUMBER_VECTORS`, **132**
`CONTAINER_VECTORS`, **12** `DEFLATE_VECTORS` and **14** `RUN_VECTORS`. The last three
are captured a different way: they run the real `testleap.exe` and store the exact input
bytes, the exit code, and the whole of stdout for each of the four output modes, CRLF
included. The container part alone is 127 archives times four modes, every one of them
compared byte for byte. Stdout is kept as bytes rather than text, because text mode would
translate CRLF to LF and quietly weaken the claim.

That corpus is corroborated outside this crate: section 2c of
`../leap-year-verification.html` records live Frida instrumentation in which the
emulated model and the running process agree on all 18 overlapping vectors.

## The ported functions

| original | name | Rust |
|---|---|---|
| `0x0042669c` | `IsLeapYear` (`Boolean IsLeapYear(Word)`) | `calendar::is_leap_year` |
| `0x004266d8` | date validate + day-number encoder | `calendar::day_number_int`, `calendar::day_number` |

Delphi calling convention, preserved: the argument arrives in `EAX`, the result is a
1-byte Boolean in `AL`, and the encoder writes through a `double*` out-parameter only
on success.

`is_leap_year` takes the full 32-bit argument register and truncates it to the
declared 16-bit `Word` parameter itself, exactly as the original does. So 65536
behaves as year 0 and 65537 as year 1. Those boundary values are in the oracle, and a
`u16` parameter could not express them.

The container validator is a chain rather than one function, so it names each piece:

| original | role | Rust |
|---|---|---|
| `0x0061a848` | `entry`, the decision chain and the verdict codes | `container::decide` |
| `0x0060df1c` | member lookup asked of the zip library | `container::has_member`, `container::has_pattern` |
| `0x00610058` | opens the archive; false means not a zip | `container::member_names` |
| `0x00611e78` | the meta check that sets verdict 7 | inside `container::decide` |
| `0x00611da8` | the meta-line echo | `container::is_meta_line`, `container::meta_echo` |
| `0x0060d88c` | member extraction by exact name | `container::read_member` |
| `0x61b414` | the `Result: %d` line the `/S` flag prints | `container::report` |

Its verdict order is 5 (not a zip), 1 (holds `masterstructure.db`, the pre-2012 layout),
3 (a required `.nx1` is absent), 4 (a forbidden pattern matches), 7 (no `sysinfo.txt`),
then 0. Two of those behaviours are bugs in the original that the port keeps, because
the goal is equivalence and not a corrected validator. Member lookup is by basename and
case-insensitive, so `sub/years.nx1` satisfies the `years.nx1` requirement. The extension
test drops exactly one trailing dot first, so `tool.exe.` is flagged while `tool.exe..`
is not. Vectors pin both.

The original also changes what it prints based on its flags, and the port models that with
The meta step also echoes the model metadata. `FUN_00611e78` takes the lines of
`sysinfo.txt` and prints the ones that begin with one of ten keys, which is how the area
name, base year, scope, regions, scenarios and time slices can be read back out of a
`.leap` file. The comparison is case-insensitive and keeps the colon, so `Area Name` with
no colon is not echoed, leading whitespace is trimmed before printing, and `/Q` and `/N`
suppress the echo while `/S` does not. Reproducing it means reading member contents, and
the archives are deflated, so `src/deflate.rs` carries a raw DEFLATE decoder written for
this crate. It stays dependency-free, like the rest of the crate, and carries its own
conformance corpus because the container vectors alone would not test it: their
sysinfo.txt bodies are tiny. `tools/capture_deflate_oracle.py` compresses 12 plaintexts
with zlib and stores each stream beside the recipe for its plaintext, so the test
rebuilds the expected bytes rather than storing them. Between them they force copies at
a one byte distance, copies at a 32000 byte distance, stored blocks, incompressible data
and four zlib levels, one of which reaches past the 32768 byte window.

The argument loop is ported as well. `container::run` takes each argument already
resolved to files, prints in argument order, and adopts the LAST verdict as the exit code
rather than the worst one, so a bad file followed by a good one exits 0. `/S` suppresses
the per-file success line while keeping the meta echo and the no-match message, and
prints a single result line at the very end rather than one per file. An archive whose
meta step aborts ends the whole run and prints no result line. No arguments at all gives
the usage text, reproduced verbatim in `container::USAGE` down to its leading bare
newline, which is the one place the original does not write CRLF.

Turning an argument into files has its own set of measured rules, all pinned by the end
to end suite rather than guessed:

* The split is on the BACKSLASH only. A subdirectory path searches in that subdirectory
  and is reported by its bare name, an absolute backslash path works, and a forward slash
  is not a separator at all.
* A forward slash anywhere makes the argument contribute nothing whatever: no message, no
  verdict, not even the no-match one. That reads like a fault rather than a rule, and it is
  the one place the port reproduces something a user would rather it did not. The library
  takes each argument already resolved, so a caller that wants forward slashes to work can
  normalise the path before handing it over.
* The name reported is the one the filesystem spells, so an upper case argument is
  reported in the lower case the file actually has, and the directory never appears.
* An argument that resolves to something unreadable, a directory in the ordinary case,
  gets its own verdict and its own message. `/S` hides that message while it does not hide
  the matched-nothing one.
* A wildcard scan reaches the dot and dot-dot entries, which are then reported as missing
  files because a directory is not something the vendor can read.

`container::parse_arguments` reproduces the vendor scan, which has a wrinkle worth
naming: a flag is recognised after dropping exactly ONE leading slash or dash, so `/Q`,
`/q`, `-Q` and `/quiet` all set quiet, but an argument only leaves the file list when its
first character is a SLASH. A dash does not count, so `-S` sets short and is then also
treated as a filename, and the vendor really does answer
`No file(s) matching: "-S" (-1)` for it. The crate also ships a `testleap` binary that
reads the files and prints, so the port is usable on its own rather than only as a
library.

`container::Flags`: the default prints one message per file, `/S` prints a single
`Result: <code>` line instead, and `/Q` prints nothing at all. The abort above is the one
exception, because the runtime prints it even under `/Q` or `/S` and the run never
reaches the result line, which is why a quiet run is not always silent. `/C` is absent
from `Flags` because its only effect is deletion, and this port deletes nothing. `/N` is
modelled only for the change it makes to the output, because the meta file its help text
promises is not written at all.

This replaced an earlier behavioural model that assumed eight forbidden extensions and
had no pre-2012 branch. Run against the same 113 vectors, that model disagreed with the
binary on 56 of them.

## Do not run the vendor tool with /C

Measured on this build, `testleap /C <files>` deletes every file it inspects whatever the
verdict: a valid archive that exits 0, one that only lacks its meta file, one that is not
a zip, and one missing required members all disappear. The help text says it deletes
disallowed LEAP files, and that is not what it does. If it has ever been pointed at a
directory of real `.leap` files, they are gone. The port recognises the `/C` spelling only
so that the argument leaves the file list where the vendor would remove it, and deletes
nothing at all.

## The model arithmetic, read out of the file

`src/expr.rs` reads the equations a LEAP area stores. This unit differs in kind from everything
above: it is a file format rather than a function in the binary, so it carries no address and
its oracle is the vendor's own data. `src/oracle_nx1_expr.rs` is generated by
`tools/capture_nx1_expr.py` and holds all 44 expressions the scenario table of the shipped
Freedonia area carries, each with the byte window it was read from.

Two things about that capture were got wrong first and are worth knowing. The alphabet includes
U+00A4, the character LEAP wraps a time-series literal in, so a reader that only accepts
printable ASCII cuts an expression short at the delimiter and reports nothing: the first
reading of the table found 28 expressions for that reason, and 16 of the 44 carry a series.
And the same tables hold URL-encoded HTML, whose `@page` rule is a wide, NUL-terminated,
printable run that looks like arithmetic until the `@F`, `@V` or `@C` marker is required.

The grammar is `@F<code>` for a function, `@V(...)` for a variable and `@C<code>` for a constant,
with numbers, `+ - * /`, parentheses and comma-separated arguments, and the series literal kept
verbatim because its internal grammar is not established. The binary corroborates the syntax
from inside rather than the corpus implying it: it formats `@F007`, `@F039` and `@F083` itself,
and its error strings say "Separate years and values with the list separator character" and
"Year parameters of the %s function are not in ascending chronological order".

What the test claims, exactly. `tests/nx1_expr.rs` asserts that the scanner returns each
expression from the original bytes, which is a second implementation of the same rule in
Python meeting this one rather than this one meeting its own output; that the token stream
carries every non-whitespace character of the source exactly once and in order; and that the
canonical form is a fixed point, so parsing it yields an equal tree that prints the same text.
It does not claim the canonical form equals the source, because LEAP is not consistent about
the spaces between arguments: `@F043(1*5, 1)` has a space after the comma while a series
literal in the same table has none.

Three mutations were run against the new suite and each was caught: dropping the series
delimiter from the alphabet, which fails the scanner test; dropping the unary minus, which
fails four; and keeping the delimiters inside the series text rather than around it, which
fails three.

What none of it establishes is what the codes mean. `@F001` wraps a value, `@F010` carries
what looks like a percentage, `@F007` a year/value series and `@F043` a pair of numbers,
but that reading comes from the shapes in the corpus rather than from an oracle, and the port
does not act on it. Evaluating the tree, and resolving a `@V` id to a branch and a year, are
later steps.

## What each function code is

`src/functions.rs` closes the other half of the arithmetic. The `@F` codes in the corpus are
not opaque: `leap.exe` builds a registry of every function its expression language can call,
and `tools/capture_function_table.py` reads all 354 entries out of that builder rather than
guessing from the expressions. Each entry carries the code, the name, the resource id the name
came from, and the second name the call site spells out.

The marker text comes from the same place. The builder formats `"000%d"` with the code, takes
the trailing three characters, and prefixes `"@F"` from a literal at address 0x01b908ec, which
is where `@F007` comes from. `functions::marker` reproduces that construction, and the corpus
test requires the file's own spelling of every code to equal it, so the registry and the parser
cannot drift apart.

Three kinds of argument had to be resolved, and the interesting one is the third. A name is a
literal, or a wide string in the image read through the PE section map, or a local filled by
`FUN_01bdcbc0(&local, id)` from a table of resource names. That last one turns out to be a plain
switch of `if (param_2 == n) { FUN_00415060(param_1, L"Name"); }`, so the resource table is
readable too and all 354 entries end up named. The first version of the tool resolved only the
first kind and managed 320; the thirty-four it could not name failed the suite, which is how
the switch was found.

The numbering is shared with a second table. Sixteen property codes, `@F175` carbon content
through `@F186` non-energy carbon stored, are registered by three functions that map a property
name to the expression that yields it, and that is what makes one corpus expression checkable
rather than merely plausible: `@F176*(1-@F185)*(@C0004/@C0003)` is the sulfur emission factor it
looks like only if 176 is sulfur content and 185 sulfur retention. The test reads both codes out
of the parsed tree and requires them to be those two properties by name.

What evaluates each name is the third table. `FUN_01b89f80` hands 332 second names, with the
address of the evaluator, to one of a family of helpers running `FUN_01b5c0c0` to `FUN_01b5c6c0`
spaced 0x60 apart, which reads like one helper per signature rather than one per function. The
dispatch folds case where the registry does not, so `_Data` there is `_data` here. Every function
the corpus calls resolves to an address through it.

The third table says what evaluates each name, and it carries arity as well. The helpers run from
`FUN_01b5c0c0` upward in steps of 0x60, one per signature, and each builds the same descriptor, fills
in the name and the evaluator address, and writes its own number at +0x10: 0 for the first helper,
1 for the second, and up to 13 before the family repeats with a different kind byte. That number is
the argument count, and it is checkable rather than merely plausible, because the vendor's stored
arithmetic has to agree with it. It does: `_gr` states 1 and every stored `@F001` call passes one
argument, `_gras` states 8 and `@F037` passes eight, `_grasel` states 9 and `@F041` passes nine,
`_AnnualizedCostSimple` states 2 and `@F043` passes two. Across the corpus that is 36 calls over
seven codes, all matching, which ties the registration in the binary to the arithmetic in the area.

Twenty-seven second names are registered by nobody, and the test pins them rather than skipping
them quietly: the plain math functions from Abs to Floor, the financial ones from Sign to Power,
and three counters. Something else evaluates those, and naming it is the next read.

Mutations for this suite ran through both the Rust and the generator. Dropping the zero padding
from the marker failed the spelling test, making `describe` stop falling back to the property
table failed the corpus test, and making the generator skip the resource switch regenerated a
table with 320 names and failed three tests.

## Typed rows out of a table

`src/records.rs` takes the step that turns an area into numbers. `nx1::dictionary` reads a table
schema and `nx1::wide_strings` reads the text out of a record area, but text is not a row: where a
field sits is stated per field in the dictionary, and this module reads it.

The dictionary is a stream of tagged properties rather than a fixed structure, and that decides
how the reader is written. A property is a tag byte and a value whose width the tag names --
`0x01` and `0x02` one byte, `0x03` two, `0x12` four, `0x06` and `0x07` a length-prefixed string,
`0x08` a flag with no value, `0x09` a nested object whose class name follows -- and only the
properties a field actually carries are written. A byte layout per field therefore does not
generalise: a first version of this reader assumed one and placed 54 of the 86 tables, and it was
wrong about three shapes it thought it could read. Walking the tokens and anchoring on the byte
pattern that introduces the ordinal places 80.

Three rules extract a field: the name is the first string after the class name, the type name is
the first string beginning with `nxt`, and the placement is the two numbers after the pattern that
precedes them. For `datanames.nx1` that gives TableID at 0 size 4, TableName at 4 size 102,
FieldID at 106, SetID at 110, Name at 114 size 302, Abbreviation at 416 and DateChanged at 518
size 8. The check is not that the reader likes its own answer: those fields tile the record with
no gap and no overlap, and the vendor's bytes then agree, spelling Balcat and Electricity with
the integers between them and every wide-string slot decoding as clean UTF-16 in all seven
records of the block.

The tiling is also the refusal rule. A layout comes back only when the fields tile from zero, so a
partial stream, a field moved by a byte, or a class name planted inside stream data -- which
`fuels.nx1` really does carry -- all produce nothing rather than a plausible wrong layout. Two
tests make that the claim rather than a property of the implementation.

Two things the file does not state, and both had to be read off the data.

The record size is zero in all eighty-six tables, because the area was written by an export
that left that descriptor field blank. It is mostly recoverable by arithmetic: a data block is
4096 bytes, the record area of each block runs to 4092, and for most tables the record size is
the smallest divisor of 4032 that is at least four bytes past the last field, which every
record then wastes in a trailing flag block. That gives 12 for years, 224 for units and
576 for datanames, and for those it is the stride the bytes are written at -- datanames
shows it directly: its seven records pitch their TableName fields exactly 576 apart, 0x040,
0x280, 0x4c0 and on. The test holds the rule against the tables it covers and requires that no
smaller divisor fit.

Not every table obeys it, and three are carried as measured strides instead of derived ones.
The evidence is the pitch of consecutive live records, which no arithmetic can fake: their
wide-string or double fields sit an exact distance apart, a whole number of pitches from the
4092 where the record area stops. staticdata measures 20 from base 0x48 against the rule's
18 -- its Expression doubles land on that pitch as 1.0, 1.0, 2021.0 and 0.0, and the header
word at 0x1e states 201, which is (4092-0x48)/20. balcat measures 304 from base 0x8c against
the rule's 336 -- thirteen fuel names, exactly 0x130 apart, ending at 4092. scenarios
measures 312 from base 0x24 against the rule's 336 -- nine names 0x138 apart, Current Accounts
through Biogas Digestion -- and its second record reads as Baseline with a memo reference to
blob block 13 and the Current Accounts parent, which is the semantics the area itself implies.
regions measures 368 from base 0x2c against the rule's 448: its freed slots hold u32 numbers
exactly 0x170 apart at 0x19c, 0x30c, 0x47c and on, and eleven records of 368 from 0x2c end at
4092. years' freed slots confirm the 0x3c indexing independently -- they hold their own slot
numbers, 33, 34, 35 and on, exactly at 0x3c + n*12. None of 20, 304, 312 or 368 divides 4032,
so the smallest-divisor rule is refuted rather than extended, and the measured pitch wins
where it exists: the layout table carries it, and the tests make the difference between
derived and measured a claim rather than an accident.
What is left, and the first item is the one that matters.

Where a table's records start in the block. The samples decode from 60 bytes in -- a 64-byte
base misaligns every string, which is how the 60 was found -- and datanames and years tile 4092
exactly from there. But the four measured tables put their first record at 0x24 (scenarios),
0x48 (staticdata), 0x8c (balcat) and 0x2c (regions), and no rule is established for that
base -- each table's record area does end at 4092 in whole strides, so base and capacity are
the same question. The header
is more than a fixed 60 bytes: word 0x1e states the live record count (years 31, balcat 13,
scenarios 9, regions 1, staticdata 201, all confirmed against what the records themselves
show), and word 0x20 onward is a used-slot bitmap with one set bit per live record, which
staticdata displays as 201 consecutive set bits. A record deleted and then freed also keeps
bytes that still look written, which is why regions.nx1 states one live row and yields ten:
the freed ones are the regions the area once had, and their RegionIDs 3 through 11 still sit
in the first field of their slots. The reader decodes them as rows and the test names that
behaviour; the bitmap is not consumed yet.

What the reader does instead is skip slots nothing was ever written to, which is a signature
rather than the file's answer: a slot is unwritten when every byte is zero, or when its first two
bytes carry its own slot number and the rest is zero, which is what a fresh block leaves behind.

The year list is what makes that checkable rather than merely plausible. With the rule,
`years.nx1` reads as exactly the 31 years 2020 to 2050 -- the base year the area's own settings
file states, through to the year LEAP stops at -- and without it the free slots read as years 33
and up. The rows also come out in insertion order, 2021 to 2030 then 2020 then 2050 down to 2031,
which is worth knowing: a caller that wants them sorted has to sort them.

Six of the 86 tables still resist, and they are named in the test rather than quietly missing:
`PluginProperties`, `Plugins`, `areadata`, `fuels`, `tedtechdata` and `uservardata`. Twenty-six
more read cleanly and hold no rows at all -- `envresults` and `results` among them -- which is a
different thing from a read failure and is recorded as such. Blob fields decode as an identifier
and no further, and the `NXHD` blocks alongside the record blocks are the blob heap, holding RTF
rather than records.

Mutations for this suite, all caught: looking for the declared length strictly after the type
name, returning a layout that does not tile, accepting any string after the class name as a field
name, reading the placement from the wrong side of its anchor, treating nothing as unwritten,
deciding that on the all-zero case alone, and comparing a slot number against the next slot
instead of its own.

## The model: the branch tree

`src/model.rs` is the first module here that reads a model rather than a file format. A LEAP area's
structure table lists every branch of the tree with its parent, its level, its kind and its name,
and that tree is what the arithmetic in the scenario table attaches to. In the shipped area it is
439 rows, 434 of them named, and the top level comes out as the eight modules the area is made of:
Load Shapes, Land Areas, Effects, Indicators, Non Energy, Stock Changes, Statistical Differences
and Freedonia itself.

The tree is worth reading because it checks itself, which nothing else in this port does yet. Every
named branch has a parent the same table holds; exactly one branch, Freedonia, has a parent that is
not a branch; and following the links from any branch reaches that root without closing a cycle.
Those are claims about the vendor's own data, and a wrong offset, a wrong record size or a wrong
slot rule would break them.

Two things to know before believing the count. The five nameless rows are slots that were written
and then freed -- ids 4 to 8, no name, parent zero -- which the unwritten-slot rule cannot tell
apart from written rows because they still carry bytes. And the level field is not the depth in
the tree: Demand is level 0 and its child Household is level 2, so the module reads the field and
does not interpret it.

The arithmetic is the part still out of reach, and this turn got as far as its address. The scenario
table keeps its expressions in a `nxtBlobWideMemo` field rather than as text inside the record, and
that field turns out to be a reference of two numbers: the second is the number of a data block in
the same file, and the first is the memo position within that block. The second number settles the
question, because the seven blocks the shipped scenario table points at are exactly the seven `NXHD`
blocks of `scenariodata.nx1`, which is not a coincidence a wrong reading would produce. The first is
bounded by them: the first data block of the table numbers its 165 memos one upwards in row order,
with the three rows that carry no expression holding zero in both fields.

So the keys are read and they join to the rest of the model: every branch a scenario row refers to is
a branch of the structure table, and every memo it points at is in one of the file's blob blocks.

The last step is reading the memo, and `src/heap.rs` does it. The framing came out of the gaps
between memos rather than out of a specification: a memo starts with a two-byte allocation and a kind
byte, the text follows in UTF-16, and the record occupies `round_up_to_four(allocation + 3)` bytes.
That last part is what took three passes, because allocations of 13, 17, 21, 31, 33, 53 and 66 sit
16, 20, 24, 36, 36, 56 and 72 bytes apart, which is the rounding and not the allocation itself. The
allocation is `2c + 1` for a text of `c` units with a floor of 13, and the text begins one byte
further along when the byte after the kind is zero, which is how the memos that open with a space are
stored.

With that, a row resolves to its expression. The first seven rows of the shipped scenario table come
out as 0.2, 5, 1000, 5, 0, 1 and 2040, in the order the rows name them, and the eighth row has no
expression at all; those are the vendor's own numbers, decoded from its block rather than from a
fixture.

A blob block states in its own header how many memos it holds, and that is what the walk is measured
against: six of the seven blob blocks of the shipped scenario table read to exactly the count they
state -- 190, 199, 149, 170, 114 and 41 -- and the seventh comes back short. That one opens with a
record whose text is longer than its allocation accounts for, and what follows it is not a record the
walk understands, so it yields one memo where 152 are stated. The reader stops rather than hunting
for the next record, so the shortfall is visible instead of quietly filled in; an earlier pass did
step forward one byte at a time, which reads that block but takes byte patterns inside the long text
for headers, and that was dropped for inventing memos rather than reading them.

Two smaller things to expect. A few memos carry no terminator inside their own record, so their text
picks up a character of the padding after it, and some hold letter values such as True and False,
which the expression reader refuses because they are values rather than arithmetic. And nothing is
evaluated: the equations read as text and not one of them has a value.

Mutations for this suite, all caught: swapping the two halves of the blob reference, reading the
variable from the region field, reading the expression from the branch field, reading the parent from
the id field, reading the level from the order field, and treating every slot as a written row.

## The differential sweep

`tools/differential_sweep.py` is the broadest check here, and it is a tool rather than a
test because it needs Python and the vendor binary. It builds archives nobody chose,
including awkward ones: backslashes and unicode in names, case-variant duplicates, empty
names, trailing dots and spaces, directory entries, both zip64 shapes, archive comments,
and random mixes. Then it runs both programs over 87 argument lists and diffs the exit
code and the whole of stdout. On the current build it reports 0 divergences over 80
archives.

Two rules came out of it that no hand-picked vector had reached.

* The member read takes the LAST case-insensitive match at the archive root, not the
  first. An archive holding both `sysinfo.txt` and `SYSINFO.TXT` is read from whichever
  was written later, so the meta echo depends on entry order. `dup_last_is_plain` and
  `dup_last_is_meta` pin it in opposite directions. A nested name never wins, however
  late it appears, because the match is on the whole root name.
* A directory entry, meaning a name ending in a slash, is not counted as a data file. An
  archive of six data members, `sysinfo.txt` and one trailing-slash entry is reported as
  seven. `dup_directory` pins that.

The sweep also caught the reader rejecting zip64 outright while the vendor read it. A
.leap large enough to need zip64 is not far fetched, so `entries` now resolves the
figures from the zip64 end-of-directory record, and from the per-entry extra field when a
central entry carries the maximum value as a placeholder for its size or its local header
offset. Neither shape occurs in a small archive written normally, so the capture script
produces both by byte surgery on the written file, and `zip64_eocd` and `zip64_entry` pin
them. The second one placeholders the `sysinfo.txt` entry, so the member read has to
resolve the placeholder before it can echo anything.

One divergence is left, and it is deliberate. Give the vendor a member whose basename is
empty, either a name of `""` or a name of `"/"`, and it dereferences a null and dies with
`EAccessViolation`. Safe Rust has no equivalent fault to reproduce, so the port treats
such a name as matching nothing and carries on. The sweep keeps those two archives in a
directory of their own so the main comparison stays a strict gate, and it fails if the
vendor ever stops faulting, which would mean the carve-out had gone stale.

## The sanctioned automation interface

The install ships a COM automation server, `LEAP.LEAPApplication`, and it is the same
surface SEI's own scripts under `_Scripts` use. It is registered on this machine, an
instance is created without a licence prompt, it runs with `Visible` false, and it exits
when the client does, so `tools/leap_api_probe.ps1` can start one, read, and quit without
leaving anything behind.

This matters more than it may look. What the port verifies so far is a file validator.
The interface exposes `Calculate`, `ForceCalculation`, `ExportResultsCSV`,
`ExportResultsXLS`, `ExportExpressions`, `Branch`, `BranchVariable`, `ResultValue` and
`CompileVarRef`, which is to say the vendor will compute a model and hand back its
numbers through a supported call. Result-level parity is therefore reachable without
emulating any of the 168,840 functions, and by the sanctioned route rather than a
reverse-engineered one. The exemplar is SEI's own `Export Data Values to Excel.vbs`,
which walks regions, branches and variables and reads `Variable.DataValue(year)`.

Measured so far: version 2026.7.0.3, and the cause of the empty collections. An
externally created instance has its NexusDB datasets closed, so every area collection
reads empty and enumerating `Areas` raises `DicAreas: Cannot perform this operation on a
closed dataset`. `Area.Open()` is the method that opens them, and it sits with `Init`,
`Save`, `Active`, `ReadOnly`, `Directory` and `Name`. The whole 209 member surface is
recorded in `docs/leap-api-surface.txt`.

So one step separates this from being an oracle: opening an area, and two things are now
known about it. The second one changes the plan.

The binary carries its own documentation. The type library help strings are embedded in
it, so the vendor describes its own interface from inside the executable, and reading
them back answers questions that probing only narrows. Areas.Add "Creates and returns a
new named area. Optionally copied from another area. If CopyFromArea is blank the new area
is created from default data". Area.Open "Opens an area (Makes it the active area)".
ActiveArea "Gets or sets the active area... Can be set equal to an area name an index or a
LEAPArea object". A scratch area built from default data would have given the oracle
without touching anything of the user's own.

It does not work, and the reason is now settled rather than guessed. The decompilation
carries the guard: chunk-00295.c line 18375 raises that message when the application is
not in an automation-clean state, and the predicate behind it, FUN_02d46f50 in
chunk-00308.c, returns false when the current screen is not the main form and carries a
flag bit at offset 0x734. Enumerating the windows of a live instance, hidden ones
included, finds 120 of them and exactly one that is visible: a TAdvMessageForm titled
Evaluation Mode. Every other form is built and hidden, including TMainfrm, TScriptFrm and
TCalcProgDialog. LEAP is simply running unlicensed on this machine, and that dialog is
what gates the area API.

So the oracle needs a licence. It is not a permission question and not a cleverer call,
and dismissing an evaluation-mode dialog from a script would be defeating the vendor
licensing, which is out of scope here for the same reason it was when this work started.
BringToFront, ShowOverview, Minimize, RefreshBranches, Clear, Refresh and a twenty second
wait were all tried first and none of them moved the gate. Nothing was created along the
way: the area count stayed at five, no folder appeared in the LEAP Areas directory, no
lock file was left, and no LEAP process remained.

Two smaller things came out of the same probe, both consequences of no area being open:
the automation WorkingDirectory is a temp folder, Temp\_LEAPWork\0, and RefreshBranches
fails with NexusDB: AliasName or AliasPath not set.

## Out of scope, on purpose

- The remaining 168,838 functions of `leap.exe`.
- The VCL user interface, the TMS `TAdv*` components and TeeChart. The port is
  headless by design.
- Turning the tables into typed rows. `nx1::dictionary` reads a table schema,
  `nx1::wide_strings` reads the text out of the record area, and both are tested against the
  vendor area. `expr` parses the arithmetic those records hold. Placing a value at a named
  field means interpreting the dictionary layout, and giving an expression a number means an
  evaluator and a resolver; those are the next steps rather than finished ones.
- Wildcard expansion inside the library. `container::run` takes each argument already
  resolved, because the order a filesystem hands back matching files is a property of the
  filesystem rather than of the program. The `testleap` binary does the expanding, in the
  current directory, sorted by name.
- `/C` deletion, deliberately rather than by oversight. See the warning above.
- The embedded CPython 3.13 and the COM automation surface.
- Anything requiring a LEAP licence. `../GHIDRA-LEAP.md` records that the shipped
  terms forbid reverse engineering and that the licence route is the sanctioned path;
  this crate is an internal study artifact, not a redistribution.

## Build and test

On this machine there is no Windows SDK, so the MSVC linker cannot run:
`C:\Program Files (x86)\Windows Kits\10` has no `Lib` directory, and no
`kernel32.lib` exists on disk. Type checking still works on the default toolchain
because it does not link:

    cargo check --all-targets

To build or test, use the user-local GNU toolchain, which ships the MinGW runtime and
`rust-lld`:

    $env:RUSTFLAGS = '-C linker=rust-lld'
    & $env:USERPROFILE\.cargo\bin\cargo.exe +stable-x86_64-pc-windows-gnu test --target x86_64-pc-windows-gnu

The crate is deliberately dependency-free, so all of this is hermetic and needs no
registry access. `cargo test` also builds the `testleap` binary, and
`tests/vendor_e2e.rs` runs it against the vendor program over 55 argument lists,
comparing the exit code and the whole of stdout byte for byte. That suite prints a note
and passes when the vendor binary is not installed, so the crate still tests elsewhere.

## Adding a function

1. Find it in `../leap-decompiled/index.tsv` and read its chunk, or in `testleap.exe`
   through the Ghidra server on port 8089.
2. Add input vectors to `tools/capture_oracle.py` for a pure function, or to
   `tools/capture_container_oracle.py` for anything observable through the process, then
   regenerate the matching `src/oracle_*.rs`.
3. Write the parity test and watch it fail.
4. Port the function, keeping its address and name.
5. Get the suite green again.
