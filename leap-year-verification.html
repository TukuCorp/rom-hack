Verifying a decompiled LEAP routine

The four-step workflow (static audit · runtime & trace · differential I/O · emulation/DBI) applied to a real function out of the LEAP decompilation. Ghidra 12.1.4 + GhidraMCP, 2026-10-12.

Target. FUN_0042669c in testleap.exe — the Delphi IsLeapYear predicate: undefined4 FUN_0042669c(uint param_1). Chosen because it is pure, self-contained, and has two in-tree callers that show how its result is consumed.

Result. Steps 1, 3 and 4 pass with evidence. Step 2 has no surface to intercept on this function, which is a finding rather than a gap. Three checklist expectations were confirmed, one was refuted, and one genuine type error in the decompilation was found and shown to be harmless.

Calling conventionfirst parameter named param_1Entry is MOV ECX,EAX: the year arrives in EAX. That is the 32-bit Borland/Delphi register convention — not SysV (rdi) or Microsoft x64 (rcx) which the checklist names. Both call sites confirm it: MOVZX EAX,word ptr [EBP-0x2] and MOV EAX,EBX immediately before CALL. EBX/ESI are saved and restored.
Types & widthsundefined4 FUN_0042669c(uint)Two real types were lost. The parameter is a 16-bit Word (MOVZX EAX,CX, MOVZX EBX,CX — only the low 16 bits are ever read), and the result is a 1-byte Boolean in AL. Correct signature: Boolean IsLeapYear(Word Year).
Compiler optimizations(param_1 & 3) == 0 for the mod-4 testmod 4 is strength-reduced to a bitwise AND EAX,0x3. But mod 100 and mod 400 are not — they remain hardware divides (MOV ESI,0x64 / MOV ECX,0x190 then DIV). No reciprocal-multiplication magic constants appear.
Refuted hypothesis. The checklist expects division by 4/100/400 to be replaced by reciprocal multiplication with magic numbers. In this binary that is true only for the mod-4 case, and only as a bitwise AND. The 100 and 400 divides are emitted literally by the Delphi compiler, so any re-implementation must reproduce integer division, not a magic-multiply approximation.

The decompilation of the leap-year function after typing, which is what the checklist is aiming at:

bool IsLeapYear(ushort Year)
{
  if (((Year & 3) == 0) && ((Year % 100 != 0 || (Year % 400 == 0)))) {
    return true;
  }
  return false;
}

The CONCAT31((int3)(param_1 / uVar1 >> 8),1) artefact and the undefined4 signature are both gone. The one blemish left is a WARNING: Unknown calling convention: this is 32-bit Delphi, whose parameter-in-EAX scheme is not one of Ghidra’s named x86 conventions, so the warning is cosmetic and the emulation evidence above (EAX in, AL out) is what actually pins the convention down.

The structure behind the boolean, resolved from memory. Both callers index a table at 0x61cef8 as leapFlag * 0x18 + month*2. Reading that memory gives two 24-byte records of twelve ushorts, days per month: 31,28,31,30,31,30,31,31,30,31,30,31 in the first and 31,29,31,30,31,30,31,31,30,31,30,31 in the second — February 0x1c versus 0x1d. So record 0 is the common year and record 1 the leap year, and IsLeapYear exists to choose between them. That is the structure the checklist asks to be defined, and the decompiler’s *(ushort *)(iVar4 + 0x61cef6 + param_2 * 2) is exactly LeapMonthLengths[leap ? 1 : 0].days[month - 1].

What this proves. The format contract was recovered from evidence and then confirmed by the binary itself. The required-member list came out of the decompilation as a contiguous array of string constants — masterstructure.nx1, areadata.nx1, scenariodata.nx1, staticdata.nx1, years.nx1 — sitting immediately before the missing required data files message. Constructing a zip with exactly those members plus sysinfo.txt produced exit 0 and the success line. Nothing was guessed that the binary did not then confirm.
What it does not prove. This exercised the container validation, not the date logic. years.nx1 is present but its contents were never parsed — placeholder bytes pass, so the leap-year branch in FUN_0042669c is not reached this way. Reaching it needs a real NexusDB years table carrying a date, which is a different and much larger piece of work than validating that the members exist.

The one real defect, and why it is benign. The decompiler typed the return as 4 bytes and rendered it as CONCAT31((int3)(param_1/uVar1 >> 8),1). The listing shows why: the true path writes only AL, leaving the upper 24 bits holding the quotient from the preceding DIV. So the function does not return 1, it returns 0x101 for 32004 and 0x201 for 65532. Both in-tree callers read only the low byte — one with MOVZX EAX,DL, the other with AND EAX,0x7f — so nothing in this binary is broken. A caller that tested the full EAX would be.

3b. Differential testing at the process level

Step 3 applied to the program rather than to a single function. TestLEAP’s container contract was re-implemented in Python and compared against the real binary across 19 crafted .leap inputs. The vectors are new combinations, not the observations the model was built from, so agreement is a prediction confirmed.

Flagged extensions, measured one at a time: .exe .com .bat .cmd .vbs .js .msi .msc. Not flagged: .dll .scr .ps1 .jar .wsh .jse .txt .nx1 .emf .zip .py .csv, and no extension at all. Matching is case-insensitive and applies to the final suffix, so a.txt.exe is flagged while a.exe.txt is not.

The harness corrected my model twice, which is the point. On the first run, 12 of 14 predictions held. Two did not: .msc came back flagged when I had predicted allowed, and meta/sysinfo.txt in a subdirectory satisfied the meta check when I had predicted a missing-meta failure. Both were amended in the model, and the same vectors then passed — followed by five new ordering vectors confirming that the checks short-circuit in the order above (a file that is both missing a data file and carrying an .exe reports 3, never 4).
Scope. This covers the container contract only. The years.nx1 contents are still never parsed, so the date logic in FUN_0042669c is not exercised by any of these 19 vectors.

4. Subroutine emulation & DBI

3c. Runtime flags, verified against the decompilation

The metadata check lives in FUN_00611e78. Its decompilation assigns the exit-code global on the missing-meta path — DAT_0062f060 = 7 — and then guards the message behind if (DAT_0062f532 == 0 && DAT_0062f530 == 0). If those globals are the quiet flags, the code should survive their suppression while the text disappears. Tested on a file with no sysinfo.txt:

FlagsExitstdout bytesText
none7145both the valid-file line and the missing-meta complaint
/Q70silent
/S79Result: 7

A prediction read off the decompiled guard, confirmed at runtime: the exit code is set before the suppression check, so it is unchanged.

File modification: a documented behaviour I could not reproduce, and I am recording that rather than skipping it. The usage text says /N suppresses meta generation, implying meta is otherwise written into the leap file. Across four scenarios — valid file with and without /N, a meta-less file, and a file carrying an executable — nothing changed: SHA-256 identical, size identical, member list identical, no .meta sidecar created, and nothing written into the Program Files install. The meta writer in FUN_00611e78 extracts labelled fields from sysinfo.txt — Area Name:, Base Year:, End Year:, Scope:, First Scenario Year:, Regions:, Scenarios:, Scenario Names:, Time Slices:, User Variables: — and a probe sysinfo.txt carrying none of those labels is the most likely reason the write never triggers here.
Why those labels matter. Three of them are years: Base Year:, End Year: and First Scenario Year:. That is the layer where year values are read from a file, and therefore the layer a date-validation bug would surface in — which is as close as this reached to the leap-year code from the file side.

Scope and limits

  • One function, deliberately. This is FUN_0042669c of the 7,647 functions in testleap.exe — and the 168.5 MB main binary leap.exe has 168,840 more. The workflow is demonstrated end-to-end here, not applied fleet-wide; reading 168k decompiled functions by hand is not what any of these four steps is for.
  • Why this function. A search of the whole decompilation for the leap-year tells (% 400, % 100, % 4, IsLeapYear) returns nothing in leap.exe and exactly this cluster in testleap.exe. It is the only leap-year routine across both binaries.
  • Step 2 is thin on purpose. For a pure register function there is no runtime surface to trace. Applying step 2 meaningfully means picking a LEAP routine that touches the filesystem or the embedded Python runtime, where API tracing has something to say.
  • Parameters arrive in EAX, not RCX. testleap.exe is 32-bit (x86:LE:32:default, borlanddelphi), so the ABI checklist items phrased around rdi/rcx do not apply as written.
